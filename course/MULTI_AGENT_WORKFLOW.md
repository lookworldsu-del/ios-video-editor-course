# 多角色教学工作流

多角色的目标是隔离职责和噪声，让主任务专注于教学决策。它不是让多个代理同时讲同一内容，也不是替学习者完成全部作业。

## 角色

| 角色 | 何时调用 | 输入 | 输出 | 写文件 |
|---|---|---|---|---:|
| 主教师 | 整章持续存在 | 章节范围、学习者回答、代码和子代理摘要 | 下一小节、统一反馈、验收决定 | 必要时 |
| `concept_teacher` | 学习者回答概念题之后 | 当前题目和回答 | 正确点、误区、缺口、一个追问 | 否 |
| `ios_coach` | 进入代码实践之后 | 当前小目标和已有代码 | 提示或小范围实现、测试结果 | 明确授权时 |
| `reviewer` | 产生代码或架构成果之后 | 改动与验收标准 | 按严重程度排列的发现 | 否 |
| `examiner` | 章末验收阶段 | 本章证据和最近回答 | 一个问题、一次评价或通过结论 | 否 |

## 每章状态机

```text
准备
  ↓
主教师讲解一个小节
  ↓
学习者复述 / 计算 / 实验
  ↓
concept_teacher 检查误区
  ↓
主教师补讲并确认
  ↓
ios_coach 指导最小实现
  ↓
reviewer 只读评审
  ↓
ios_coach 按需修正，主教师验证
  ↓
examiner 一次一题验收
  ↓
主教师决定通过并更新 PROGRESS.md
```

不是所有章节都有代码；纯概念章节可以跳过 `ios_coach` 和 `reviewer`，但不能跳过学习者练习与验收。

## 并行规则

适合并行：

- 对已经完成的代码分别检查正确性和测试缺口。
- 代码路径探索与 Apple 官方 API 核对。
- 独立测试运行和只读日志分析。

必须顺序：

- 概念讲解 → 学习者回答 → 误区诊断。
- 领域规则 → 最小代码 → 评审 → 修正。
- 学习过程 → 面试验收 → 更新进度。

多个写代理不得并行工作，防止代码冲突和学习过程被自动化结果淹没。

## 主教师委派模板

概念诊断：

```text
委派 concept_teacher。只检查学习者对当前小节回答的理解，返回正确点、误区、缺口和一个追问。不要改文件。等待它返回后，由主教师统一反馈。
```

实践指导：

```text
委派 ios_coach。围绕当前章节的这个最小目标检查已有代码，先给学习提示；只有我明确要求实现时才修改文件。完成后返回验证结果和一个让学习者复述的问题。
```

代码评审：

```text
委派 reviewer。只读评审当前章节改动，重点检查时间语义、生命周期、并发、错误恢复和测试。按严重程度返回具体发现，不修改代码。
```

章节验收：

```text
委派 examiner。根据本章完成标准和已有证据，只生成一个验收问题，或评价学习者最近一个回答。未达到标准时不要判定通过。
```

## 学习者可直接使用的启动 Prompt

```text
本章启用项目内多角色教学。主任务担任主教师并统一与我交流，严格按照 course/MULTI_AGENT_WORKFLOW.md 的状态机分配 concept_teacher、ios_coach、reviewer 和 examiner。不要一次启动所有角色，不要让多个代理同时改代码。现在只开始当前章节的第一个小节。
```
